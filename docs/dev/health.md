# Παρακολούθηση παραγωγής (health check)

**Τι απαντά:** «ανοίγει η σελίδα αυτή τη στιγμή;» — ερώτηση που το CI **δεν**
απαντά.

## Γιατί υπάρχει

Στις 27–28/07/2026 ολόκληρο το δημόσιο site ήταν κάτω περίπου **24 ώρες**. Το
έμαθε ο ιδιοκτήτης με το μάτι του· κανένας αυτοματισμός δεν φώναξε.

Σε όλη τη διάρκεια της διακοπής:

- το CI ήταν **πράσινο**,
- το `npm run build` περνούσε **καθαρά**,
- και τα **74 test suites** περνούσαν.

Η αιτία ήταν σφάλμα στην **απόδοση (SSR)**, όχι στη μεταγλώττιση: Server
Components διάβαζαν τιμή από module `'use client'` και έπαιρναν `undefined`.
Ο TypeScript δεν το βλέπει (ο τύπος είναι σωστός, η τιμή στον χρόνο εκτέλεσης
δεν είναι) και το build δεν το βλέπει (το σφάλμα συμβαίνει όταν αποδίδεται η
σελίδα, όχι όταν χτίζεται).

> **Το μάθημα: το πράσινο CI δεν σημαίνει ότι η σελίδα ανοίγει.**

Δύο ανεξάρτητα δίχτυα προέκυψαν από αυτό και χρειάζονται **και τα δύο**:

| | Πότε | Τι πιάνει |
|---|---|---|
| `scripts/check-server-imports.mjs` (στο CI) | πριν το merge | τη **συγκεκριμένη** αιτία, στατικά |
| `scripts/health-check.mjs` (αυτό εδώ) | κάθε 15′ στην παραγωγή | **οποιαδήποτε** αιτία, εκ των υστέρων |

Το πρώτο εμποδίζει αυτό το σφάλμα να ξαναφτάσει στην παραγωγή. Το δεύτερο
εμποδίζει *οποιοδήποτε* σφάλμα να μείνει 24 ώρες αόρατο.

## Τι ελέγχεται

Οι δημόσιες διαδρομές — ό,τι βλέπει κάποιος χωρίς λογαριασμό:

`/` · `/login` · `/signup` · `/trust` · `/privacy` · `/terms` · `/offline`

Μια διαδρομή θεωρείται **υγιής μόνο αν ισχύουν όλα**:

1. κωδικός **200**·
2. το σώμα **δεν** περιέχει «Κάτι πήγε στραβά»·
3. το σώμα δεν είναι ουσιαστικά άδειο (≥ 500 χαρακτήρες)·
4. στην αρχική, το σώμα περιέχει «**PROPERWISE**».

Κάθε διαδρομή δοκιμάζεται έως **3 φορές με 5″ αναμονή** πριν χαρακτηριστεί
αποτυχία, ώστε μια στιγμιαία αστοχία δικτύου ή ένα cold start να μη σημάνει
ψευδή συναγερμό. Ένα ειδοποιητικό που χτυπά για ψέματα το αγνοεί ο άνθρωπος —
και τότε δεν χτυπά ούτε για την αληθινή διακοπή.

### Γιατί δεν αρκεί ο κωδικός status — το κρίσιμο σημείο

Η σελίδα σφάλματος του Next (`app/error.tsx`, `app/global-error.tsx`) είναι
*error boundary*, όχι HTTP σφάλμα: **γυρίζει κανονικό `200 OK`**.

Δηλαδή στη διακοπή του Ιουλίου 2026 κάθε δημόσια διεύθυνση απαντούσε `200`
ενώ ο επισκέπτης έβλεπε «Κάτι πήγε στραβά». **Ένας έλεγχος μόνο στον κωδικό
status θα ήταν πράσινος και τις 24 ώρες** — θα είχε προσθέσει ψεύτικη ησυχία
αντί για ασφάλεια. Γι' αυτό ο έλεγχος διαβάζει το **σώμα** της απάντησης.

Ο έλεγχος #4 (αναμενόμενο περιεχόμενο) καλύπτει το συμπληρωματικό σενάριο: μια
απάντηση `200`, χωρίς μήνυμα σφάλματος, αλλά **άδεια ή ακρωτηριασμένη**
(μισοτελειωμένο stream, λάθος rewrite, σελίδα-φάντασμα του CDN) δεν πρέπει να
περνά για υγιής.

> Αν αλλάξει ποτέ το κείμενο της σελίδας σφάλματος ή το «PROPERWISE» της
> αρχικής, **πρέπει** να ενημερωθεί το `scripts/health-check.mjs` — αλλιώς ο
> έλεγχος ξαναγίνεται σιωπηλά τυφλός.

## Πότε τρέχει

`.github/workflows/health.yml`:

- **κάθε 15 λεπτά** (`cron: */15 * * * *`) — ορίζει το χειρότερο παράθυρο
  άγνοιας: ~15′ αντί για ~24 ώρες·
- **μετά από κάθε push στο `main`**, με **αναμονή 90″** πρώτα. Στο push το
  Vercel μόλις *ξεκινάει* το build και η παραγωγή σερβίρει ακόμη το προηγούμενο
  deployment· χωρίς την αναμονή ο έλεγχος θα επιβεβαίωνε την παλιά έκδοση,
  δηλαδή θα έβγαινε πράσινος ακριβώς για το commit που μόλις έσπασε το site·
- **χειροκίνητα** (`workflow_dispatch`) για επιβεβαίωση μετά από διόρθωση.

Ο προγραμματιστής του GitHub είναι *best-effort*: υπό φόρτο τα cron runs
καθυστερούν. Επίσης, σε repo χωρίς δραστηριότητα για **60 ημέρες** το GitHub
απενεργοποιεί τα scheduled workflows — αν σταματήσουν τα runs χωρίς προφανή
λόγο, αυτός είναι ο πρώτος ύποπτος.

## Τι γίνεται σε αποτυχία

Ανοίγει issue με **σταθερό τίτλο** «Η παραγωγή δεν απαντά σωστά» και ετικέτα
`health-failure`, που περιέχει τον πίνακα με το ποια διαδρομή έπεσε και γιατί.

- Αν υπάρχει **ήδη ανοιχτό** τέτοιο issue, προστίθεται **σχόλιο** αντί για νέο
  issue. Χωρίς αυτό, ένας 15λεπτος έλεγχος θα άνοιγε **96 issues την ημέρα**
  (4×24) και ο ιδιοκτήτης θα σταματούσε να τα διαβάζει την πρώτη μέρα. Τα
  διαδοχικά σχόλια δείχνουν και τη **διάρκεια** της διακοπής.
- Μόλις ο έλεγχος ξαναγίνει πράσινος, το issue **κλείνει αυτόματα** με σχόλιο
  που λέει ποιο run το έλυσε. Ένα ειδοποιητικό που ανοίγει αλλά δεν κλείνει
  ποτέ παύει να είναι ειδοποιητικό: το κόκκινο μένει για πάντα και το επόμενο
  πραγματικό πρόβλημα δεν ξεχωρίζει από το παλιό. (Ίδιο μοτίβο με το
  `resolve-on-success` στο `.github/workflows/supabase-deploy.yml`.)

Δικαιώματα: μόνο `issues: write` και `contents: read`.

## Ρύθμιση της διεύθυνσης — `HEALTH_BASE_URL`

Χωρίς ρύθμιση ελέγχεται το **default `https://property-tan-gamma.vercel.app`** και
το workflow το **δηλώνει με `::warning::`** στο log. Αυτό είναι σκόπιμο: ο πιο
ύπουλος τρόπος να αποτύχει ένα monitor είναι να ελέγχει σιωπηλά λάθος
διεύθυνση και να μένει πράσινο ενώ το πραγματικό site είναι κάτω.

**Όταν ο ιδιοκτήτης συνδέσει δικό του domain:**

1. GitHub → repo → **Settings** → *Secrets and variables* → **Actions** →
   *New repository secret*
2. Name: `HEALTH_BASE_URL`
3. Secret: η βάση URL **χωρίς κάθετο στο τέλος**, π.χ. `https://properwise.gr`
4. **Actions** → *Health* → **Run workflow** και επιβεβαίωσε στο log ότι δεν
   εμφανίζεται πλέον το warning για το default.

> Το `HEALTH_BASE_URL` είναι secret μόνο για λόγους ρύθμισης — η τιμή του είναι
> μια δημόσια διεύθυνση, όχι διαπιστευτήριο. Εμφανίζεται στην αναφορά του issue.
> Μη βάλεις ποτέ εκεί URL με token ή κωδικό μέσα.

## Τοπική εκτέλεση

```bash
node scripts/health-check.mjs https://property-tan-gamma.vercel.app
# ή
HEALTH_BASE_URL=http://localhost:3000 node scripts/health-check.mjs
```

Το πρώτο όρισμα υπερισχύει της μεταβλητής, ώστε να δοκιμάζεται εύκολα άλλο
περιβάλλον (preview, staging, localhost) χωρίς αλλαγή ρυθμίσεων. Τρέχει με
σκέτο `node` — **καμία εξάρτηση**, ώστε ο έλεγχος που μας λέει αν ζει η
παραγωγή να μην εξαρτάται από τη διαθεσιμότητα του npm registry. Έξοδος `1` αν
έστω μία διαδρομή αποτύχει.

## Τι ΔΕΝ καλύπτει

Σημαντικό να είναι ρητό, ώστε το πράσινο να μη διαβάζεται ως κάτι παραπάνω από
ό,τι είναι:

- **Σελίδες πίσω από σύνδεση.** `/dashboard`, `/portal`, οι ρυθμίσεις — τίποτα
  από αυτά. Ο έλεγχος τρέχει ανώνυμα και δεν κρατά διαπιστευτήρια. Το
  `/dashboard` μπορεί να είναι εντελώς σπασμένο με τον έλεγχο πράσινο.
- **Διαδρομές με παράμετρο**: `/checkin/[token]`, `/accountant/[token]`,
  `/verify/[id]`, `/unsubscribe/[token]` — χρειάζονται έγκυρο token.
- **Το API και οι edge functions.** Ελέγχονται μόνο σελίδες HTML.
- **Η βάση.** Μια σελίδα μπορεί να αποδίδεται μια χαρά ενώ η Supabase είναι
  κάτω — η αρχική είναι σχεδιασμένη να το αντέχει αυτό (`try/catch` γύρω από τη
  συνεδρία στο `app/page.tsx`). Για τη βάση υπάρχουν τα `db-backup.yml` και
  `backup-watchdog.yml`.
- **Σωστά δεδομένα ή σωστοί υπολογισμοί.** Ελέγχεται ότι η σελίδα *αποδίδεται*,
  όχι ότι τα νούμερα είναι σωστά· αυτό είναι δουλειά του `npm run test`.
- **Οπτικές παλινδρομήσεις.** Ένα κατεστραμμένο layout που όμως αποδίδεται
  περνά ως υγιές.
- **Απόδοση/ταχύτητα.** Ο χρόνος τυπώνεται στον πίνακα αλλά δεν υπάρχει όριο
  που να ρίχνει τον έλεγχο· μόνο το timeout των 20″ ανά αίτημα.
