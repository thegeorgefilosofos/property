# Η τροφοδοσία των στεγαστικών επιτοκίων — τι τρέχει, πού και πώς το ελέγχεις

## Τι βρέθηκε στην παραγωγή (02/09/2026)

Η οθόνη του Δανείου έγραφε «Τα επιτόκια επιβεβαιώθηκαν πριν από 56 ημέρες».
Στη βάση: και οι επτά τράπεζες με `verified_at = 2026-07-08`, πηγή vresdaneio.gr.

Η εργασία `bank-rates-monthly` υπήρχε στον `cron.job`, ενεργή, με χρονοδιάγραμμα
`30 6 1 * *` — και **δεν είχε τρέξει ποτέ**: προγραμματίστηκε την 1η Σεπτεμβρίου
μετά τις 06:30 UTC, δηλαδή λίγες ώρες μετά τη μοναδική της θέση για τον μήνα. Στο
`cron.job_run_details` δεν υπάρχει καμία γραμμή της. Η συνάρτηση
`bank-rates-updater` είναι ανεβασμένη (έκδοση 19) και ο δρόμος pg_net → function
δουλεύει (η `market-data-daily` απαντά 200 κάθε πρωί).

Ακόμη κι αν έτρεχε, δεν θα άφηνε ίχνος σε αποτυχία: το μόνο σημάδι ζωής ήταν το
`verified_at`, που αλλάζει μόνο σε επιτυχία. Αποτυχία και σιωπή ήταν το ίδιο.

Από το περιβάλλον ανάπτυξης οι σελίδες των τραπεζών, το e-stegastiko.gr και το
vresdaneio.gr **δεν είναι προσβάσιμα** (egress κλειστό). Καμία τιμή δεν γράφτηκε
με το χέρι: οι σημερινές τιμές θα έρθουν από το πρώτο πέρασμα της συνάρτησης,
που ζει σε περιβάλλον με δίκτυο.

## Το δεύτερο εύρημα: το staging καλούσε την παραγωγή

Ψάχνοντας γιατί δεν έτρεχε η εργασία, βρέθηκε κάτι μεγαλύτερο. Το vault secret
`functions_base_url` **δεν υπήρχε σε κανένα από τα δύο έργα** και το εφεδρικό
που γράφουν όλες οι μεταναστεύσεις είναι το ref της παραγωγής, καρφωμένο. Στην
παραγωγή αυτό είναι σωστό κατά τύχη· στο staging σήμαινε ότι **εννιά εργασίες
cron καλούσαν τις συναρτήσεις της παραγωγής**:

```
bank-rates-daily · email-outbox-schedule · ical-sync-3h · market-data-daily
purge-orphan-files · send-market-digest-weekly · send-monthly-statements
send-newsletter-weekly · send-reminders-daily
```

Δεν έγινε ζημιά επειδή το `x-cron-secret` του staging δεν ταιριάζει με της
παραγωγής: κάθε κλήση γύριζε 401, κάθε πέντε λεπτά, επί μήνες. Μας έσωσε ο
έλεγχος ταυτότητας, όχι ο σχεδιασμός — και στη λίστα είναι το
`purge-orphan-files`, που σβήνει αρχεία και τρία που στέλνουν email σε
πραγματικούς παραλήπτες.

Διορθώθηκε (`20260902140000`): το μυστικό ορίστηκε ρητά και στα δύο έργα, η
διεύθυνση διαβάζεται πλέον από `private.functions_base_url()` χωρίς εφεδρικό και
η μετανάστευση ξαναγράφει κάθε εργασία που δείχνει σε ξένο έργο. Φύλακας
`guard-project-ref` ώστε να μην ξαναγραφτεί καρφωμένο ref.

Επαληθεύτηκε στο staging: 0 εργασίες προς την παραγωγή, 9 προς το ίδιο το έργο.

## Πώς ανεβαίνει

```
supabase db push                                        # η μετανάστευση: πίνακες, υγεία, cron, πρώτο πέρασμα
supabase functions deploy bank-rates-updater --no-verify-jwt
supabase secrets set ANTHROPIC_API_KEY="sk-ant-..."     # αν δεν υπάρχει ήδη
```

Η σειρά έχει σημασία μόνο για το πρώτο πέρασμα: αν η συνάρτηση ανέβει ΜΕΤΑ τη
μετανάστευση, το πρώτο πέρασμα θα χτυπήσει την παλιά έκδοση, που δεν γράφει
ίχνος. Το επόμενο πρωί τρέχει η νέα. Για να μην περιμένεις:

```sql
select net.http_post(
  url := 'https://aromvduuxtcrzmwwvnej.supabase.co/functions/v1/bank-rates-updater',
  headers := jsonb_build_object('Content-Type','application/json',
             'x-cron-secret', (select secret from public.cron_secrets where name = 'email_cron')),
  body := '{}'::jsonb, timeout_milliseconds := 180000);
```

## Τι επαληθεύτηκε στο staging (02/09/2026)

Χειροκίνητο πέρασμα με τη νέα συνάρτηση, μέσω `private.functions_base_url()`:

| | αποτέλεσμα |
|---|---|
| απάντηση HTTP | `200` (πριν: `401`, γιατί η κλήση πήγαινε στην παραγωγή) |
| σώμα | `{"ok":false,"error":"ANTHROPIC_API_KEY not set"}` |
| `bank_rate_checks` | μία γραμμή: `false · ANTHROPIC_API_KEY not set` |
| `bank_feed_health()` | `ok=false`, `reason='το τελευταίο πέρασμα απέτυχε: ANTHROPIC_API_KEY not set'` |

Το staging δεν έχει κλειδί Anthropic, οπότε η αποτυχία είναι η αναμενόμενη. Αυτό
που αποδεικνύεται είναι το ζητούμενο: **μια αποτυχία αφήνει πλέον ίχνος**. Πριν,
το ίδιο πέρασμα θα τελείωνε σιωπηλά και η οθόνη θα συνέχιζε να μετρά ημέρες.

## Τι κοιτάς για να πεις «δουλεύει»

```sql
select * from public.bank_feed_health();          -- ok, reason, last_check, verified_at, held_changes
select * from public.bank_rate_checks order by ran_at desc limit 5;
select * from public.bank_feed_held();            -- οι κρατημένες της εβδομάδας
select bank_id, fixed_5yr, verified_at, source_url from public.bank_rates order by fixed_min;
select jobname, schedule, active from cron.job where jobname like 'bank-%';
```

- `bank_rate_checks` χωρίς γραμμή 48 ώρες → η εργασία δεν τρέχει (βλ. `cron.job_run_details`, `net._http_response`).
- Γραμμή με `ok = false` και `reason` που αρχίζει με `anthropic 401/400` → κλειδί ή μοντέλο.
- `insufficient_valid_rows` συνεχόμενα → η αναζήτηση δεν βρίσκει τις σελίδες· η οθόνη κρατά τις παλιές τιμές και το λέει.
- Κρατημένες μεταβολές που δεν επιβεβαιώνονται ποτέ → κοίτα την πηγή στο `source_url` και γράψε τη σωστή τιμή στη φόρμα του διαχειριστή (καρτέλα Δάνειο).

## Τι ΔΕΝ κάνει

- Δεν είναι push από τις τράπεζες: τέτοιο feed δεν υπάρχει. Μία ερώτηση την
  ημέρα είναι το «πραγματικό χρόνο» που επιτρέπει η πηγή.
- Δεν εφαρμόζει μεγάλες μεταβολές με ένα πέρασμα, ακόμη κι αν είναι σωστές·
  εφαρμόζονται την επόμενη μέρα, όταν το δεύτερο πέρασμα συμφωνήσει.
- Το κουμπί «Αυτόματη επικαιροποίηση με AI» του διαχειριστή καλεί τη συνάρτηση
  με JWT χρήστη, που η συνάρτηση επίτηδες δεν δέχεται (μόνο service key ή cron
  secret). Ηταν έτσι και πριν· ο σωστός δρόμος είναι το SQL πιο πάνω.
