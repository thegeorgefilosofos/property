# Ένας τύπος για το ακίνητο και τον χρήστη — οδηγός εκτέλεσης

Γραμμένο 14 Αυγούστου 2026, μετά από χαρτογράφηση και αντιπαράθεση δύο
ανεξάρτητων περασμάτων πάνω στα αρχεία των μεταναστεύσεων.

## Γιατί αυτό είναι οδηγός και όχι μετανάστευση

Η αλλαγή σβήνει και ξαναγράφει **πενήντα οκτώ πολιτικές ασφαλείας**. Δύο
πράγματα πρέπει να ισχύουν για να γραφτεί σε αρχείο μέσα στο `supabase/migrations/`:

1. Να μπορεί να **εφαρμοστεί και να επαληθευτεί** την ίδια ώρα, πάνω στη
   βάση δοκιμών και μετά στην παραγωγή.
2. Ο αγωγός να είναι **πράσινος**, ώστε το αρχείο να μη μείνει άγραφο στη βάση
   ενώ ο κώδικας της εφαρμογής προχωράει σαν να εφαρμόστηκε.

Σήμερα δεν ισχύει κανένα από τα δύο: ο `supabase-deploy.yml` αποτυγχάνει από τις
11 Αυγούστου, και η σύνδεση διαχείρισης της Supabase δεν είναι διαθέσιμη σε
αυτή τη συνεδρία. Ένα αρχείο μετανάστευσης που σβήνει πολιτικές ασφαλείας και
κάθεται ανεφάρμοστο είναι χειρότερο από το πρόβλημα που λύνει.

**Ο οδηγός εκτελείται σε ΕΝΑ παράθυρο, με ανοιχτή σύνδεση, σε μία συναλλαγή.**

## Τι διορθώνεται

Δέκα πίνακες κρατούν το `property_id` ως `text` ενώ το `user_properties.id`
είναι `uuid`: `checkin_links`, `client_stays`, `guest_checkins`, `ical_feeds`,
`inventory_handovers`, `inventory_items`, `inventory_maintenance`,
`maintenance_requests`, `portal_links`, `pricing_settings`.

Τρεις κρατούν και το `user_id` ως `text`: `inventory_items`, `airbnb_bookings`,
`tenant_comm_log`.

Τα δύο πραγματικά κόστη σήμερα, και τα δύο σε μονοπάτι που τρέχει **ανώνυμος
χρήστης**:

| Πού | Τι κοστίζει |
|---|---|
| `get_checkin_context` (20260723100000:82) | `where id::text = v_link.property_id::text` ακυρώνει το πρωτεύον κλειδί του `user_properties`: σειριακή σάρωση όλων των ακινήτων όλων των πελατών σε κάθε φόρτωση της σελίδας δήλωσης άφιξης |
| `declare_rent_payment` (20260806220000:38) | `rp.property_id::text = v_link.property_id::text` σε UPDATE, από τον ενοικιαστή που δηλώνει πληρωμή |

Τα υπόλοιπα είναι δομικά: χωρίς ενιαίο τύπο δεν μπαίνουν ξένα κλειδιά, και το
σβήσιμο ακινήτου εξαρτάται από σκανδάλη αντί για CASCADE.

## Πέντε πράγματα που ΘΑ ΣΠΑΣΟΥΝ αν δεν προβλεφθούν

Αυτά βγήκαν από αντιπαράθεση, όχι από ανάγνωση. Καθένα έχει επαληθευτεί στο
αρχείο του.

### 1. Το στιγμιότυπο ΔΕΝ βγαίνει από τα αρχεία

Η `20260808010000_rls_initplan.sql:73` σαρώνει τον κατάλογο και εκπέμπει
`alter policy` για κάθε πολιτική που καλεί `auth.uid()`, αντικαθιστώντας την με
`(select auth.uid())`. **Κανένα `CREATE POLICY` δεν γράφτηκε.** Άρα οι 22
πολιτικές του baseline έχουν σήμερα διαφορετικό σώμα από αυτό που δείχνει το
αρχείο τους.

Το στιγμιότυπο πρέπει να βγει από `pg_get_expr(polqual, polrelid, true)` και
`pg_get_expr(polwithcheck, polrelid, true)`. Και προσοχή: η Postgres
ξανατυπώνει το υποερώτημα ως `( SELECT auth.uid() AS uid)` — **το `AS uid`
είναι μέρος του κειμένου** και πρέπει να το προβλέπει κάθε έκφραση
αντικατάστασης.

### 2. Η σκανδάλη `purge_property_children` σκάει σε κάθε διαγραφή

`20260814090000_referential_integrity.sql:90`:

```sql
execute format('delete from public.%I where property_id = $1', t) using old.id::text;
```

Με στήλη `uuid` γίνεται `uuid = text` → **42883 σε κάθε διαγραφή ακινήτου, για
κάθε χρήστη**. Η σκανδάλη και η συνάρτησή της πέφτουν **πριν** το `alter`, στην
ίδια συναλλαγή με τα δέκα νέα ξένα κλειδιά `on delete cascade` που την
αντικαθιστούν. Το σχόλιό της (:77-78) το προβλέπει ρητά.

### 3. Ο φάκελος του λογιστή σκάει στο πρώτο άνοιγμα

`20260814090000:418` είναι ο τελευταίος ορισμός της `get_accountant_data`:

```sql
where s.property_id = p.id::text and s.user_id = v_link.user_id
```

Οι διπλανές γραμμές (:396, :402, :413) συγκρίνουν ήδη `= p.id` χωρίς cast. Η
:418 είναι η μοναδική εξαίρεση, και μετά την αλλαγή τύπου γίνεται `uuid = text`.
**Υποχρεωτικά στην ίδια μετανάστευση.**

### 4. Η μετεγγραφή πρέπει να είναι αυστηρά περιορισμένη στους 12 πίνακες

Στους δικούς μας πίνακες το cast είναι πάντα **μονόπλευρο**:
`(p.id)::text = <t>.property_id`. Γειτονικές πολιτικές του ίδιου baseline
(`bills`:4479, `checklist_items`:4487, `contacts`:4507, `expenses`:4515,
`loans`:4539) γράφουν **διπλό** cast: `(p.id)::text = (<t>.property_id)::text`.
Αν ο βρόχος πιάσει και αυτές, τις χαλάει.

Και μία παγίδα μέσα στους 12: η `Service write inventory_handovers`
(baseline:4193) έχει `auth.role() = 'service_role'::text`. Είναι **κυριολεκτική
τιμή**, όχι στήλη. Μια «απλοποιημένη» μετεγγραφή που σβήνει κάθε `::text` της
αφαιρεί τον τύπο και ο ρόλος υπηρεσίας χάνει την εγγραφή στα πρωτόκολλα
παράδοσης.

### 5. Οι `parent_upd_*` έχουν WITH CHECK χωρίς USING

`20260810060000:100-104` δημιουργεί `as restrictive for update with check (…)`
**χωρίς** `using`, και η αιτιολογία στις :31-34 είναι ρητή: «ένα restrictive
USING θα τις έκρυβε από τον ίδιο τον ιδιοκτήτη τους». Ο κώδικας ανακατασκευής
εκπέμπει ρήτρα **μόνο** όταν το `pg_get_expr` δεν είναι `null`.

## Η σειρά

```
 0. ΠΡΟΠΤΗΣΗ, σε ξεχωριστή συναλλαγή που γυρίζει πίσω:
    α) καμία τιμή εκτός μορφής uuid στις 13 στήλες  (case-SENSITIVE έλεγχος)
    β) κανένα ορφανό property_id
    γ) καμία σύγκρουση μοναδικότητας μετά τη μετατροπή

 1. begin;

 2. ΑΠΟΤΥΠΩΜΑ «ΠΡΙΝ»: για κάθε χρήστη και κάθε πίνακα, count(*) από SELECT
    ΚΑΙ αποτέλεσμα δοκιμαστικής εγγραφής σε ΞΕΝΟ ακίνητο (πρέπει να αποτυγχάνει).
    ΜΗΝ βάλεις τις 13 στήλες στο md5 — η πεζότητα του uuid αλλάζει με το cast.

 3. Στιγμιότυπο πολιτικών από pg_policies + pg_get_expr σε προσωρινό πίνακα.

 4. drop trigger trg_purge_property_children; drop function purge_property_children;

 5. drop policy για τις 58.

 6. alter column … type uuid using property_id::uuid   (10 πίνακες)
    alter column … type uuid using user_id::uuid       (3 πίνακες)

 7. create policy από το στιγμιότυπο, με τις δύο μετεγγραφές:
       (p.id)::text                      →  p.id
       (( SELECT auth.uid() AS uid))::text →  ( SELECT auth.uid() AS uid)
    Ρήτρα μόνο όπου υπήρχε.

 8. ΦΡΑΧΤΗΣ: σκάσε αν έμεινε οποιοδήποτε ::text μέσα σε έκφραση που αναφέρει
    p.id / property_id / user_id. Μην βασιστείς σε regex με αγκίστρωση —
    το ` AS uid))` παρεμβάλλεται.

 9. Ξένα κλειδιά on delete cascade στους δέκα, και στους τρεις προς auth.users.

10. Διόρθωση των τεσσάρων συναρτήσεων: get_accountant_data:418,
    get_checkin_context:82, declare_rent_payment:38, και τα ::uuid του
    get_portal_data / submit_maintenance_request που γίνονται περιττά.

11. Ξανατρέξε τους ελέγχους πλήθους της 20260810060000:108-121 (62 και 32).

12. ΑΠΟΤΥΠΩΜΑ «ΜΕΤΑ». Ίδιο με το βήμα 2, ανάγνωση ΚΑΙ εγγραφή. Διαφορά → rollback.

13. commit;
```

## Τι ΔΕΝ κάνει αυτή η μετανάστευση

Δεν ρίχνει τις υπερφορτώσεις κειμένου των `private.member_sees_property`,
`private.member_sees_financials`, `private.owns_parent_property`. Μόλις
μηδενιστούν οι στήλες κειμένου γίνονται νεκρός κώδικας για τις πολιτικές — αλλά
το `scripts/db/rls-probe.sql:242-253` τις καλεί ρητά και απαιτεί η ανεκτική
διαδρομή να δέχεται μη-uuid. Ξεχωριστό αρχείο, μαζί με ενημέρωση του probe,
αλλιώς σπάει το CI αντί για την παραγωγή.
